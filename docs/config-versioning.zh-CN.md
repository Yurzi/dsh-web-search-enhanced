# 插件配置版本与自动迁移设计

## 决策

需求合理。沿用已有顶层 `version` 作为 schema version，不另设 `schemaVersion`，避免双字段冲突。当前版本为整数 **2**，由共享的 `CURRENT_CONFIG_VERSION` 管理。它与 npm 包版本、宿主版本、SettingsForms revision（并发控制）、会话 Storage Domain version 相互独立。

不因每次发布而递增；只有配置结构或解释语义发生不兼容变化时递增。新增兼容的可选字段一般不递增。

## 版本判定

| 输入 | 行为 |
| --- | --- |
| 无版本且包含历史模型字段 | 视为 V1，自动迁移 |
| 显式 version: 1 | 自动执行 1 → 2，即使没有其他历史字段 |
| 无版本的连接配置或空配置 | 固定视为历史 V2；不因启动写入版本覆盖 |
| version: 2 | 校验后直接使用，无重复迁移 |
| 高于当前版本 | 拒绝读取/提交，不尝试降级或重置 |
| 非正安全整数、字符串、null | 拒绝，不猜测版本 |

显式版本优先于字段启发式判定。无版本连接格式永久映射到 **2**，以后升级到 V3 也不能把它直接认作 V3。设置卡片实际写入新值时补齐当前版本；无操作或恢复继承不制造无意义覆盖。手工编写的配置建议始终声明版本。版本字段不能设置 schema 默认值，否则宿主合并默认值可能把旧配置伪装成新版。

## 迁移流程

1. Loader schema 接受数字版本，让已知旧版本能够进入迁移校验；插件负责严格的版本范围判定。
2. `migrateConfig` 克隆输入，按注册表顺序执行 N → N+1 的纯转换，检查每一步输出版本，最后校验当前连接结构。失败不修改输入，不执行 I/O。
3. V1 转换保留现有连接、freshness、显式 defaultConnection 等非历史字段；只有没有显式默认时才选择导入的连接。已有 custom:legacy 冲突则拒绝，而非覆盖。旧 fallbackModel 不再转为备用路由。
4. 宿主启动完成及本插件设置更新后，读取该条目的实时 descriptor。仅需要升级时生成迁移结果。
5. 对旧明文 Key，先验证无秘密的转换结果，再确保 Credentials 中已有相同值或完成写入；不同值不覆盖。配置版本判定在剥离 Key 前进行，避免仅有 apiKey 的旧配置被误认作 V2。
6. 使用宿主 SettingsForms.replace(namespace, migrated, revision) 提交，只修改本插件条目。版本与转换结果一起提交，不先单独写版本。
7. 单实例迁移串行执行，执行中收到更新会标记待处理；结束后重新读取最新 revision。CAS 冲突不会覆盖新配置。失败的相同 revision 不持续重试；配置更新、凭据服务重新挂载或插件重启可重试。
8. 未迁移完成的旧配置不执行搜索；未来版本由配置校验拒绝。客户端设置编辑和重置也拒绝未迁移/未来版本。

## 边界与恢复

- 使用宿主已有的配置编辑与持久化契约，不直接写配置文件，不修改宿主源码。
- Credentials 与 profile 不是跨服务事务：凭据可能已写入而 profile 提交失败。保留该凭据，重试复用；不回滚删除可能被其他操作引用的凭据。
- 宿主 replace 会与继承层合并，不能保证清除 bundle 源码中的历史字段或秘密；继承层明文 Key 必须由部署者移走。旧配置备份也不由插件自动销毁。
- 不自动改变已有会话选择，不探测供应商，不新增联网请求；正在运行的搜索仍使用冻结快照。
- 不支持自动降级。恢复旧插件前应恢复与之匹配的配置备份，而非手工降低版本数字。
- 对需要新授权、信息丢失或无法可靠推断的未来变更，迁移步骤应明确失败并提示人工处理；“无感”不是静默猜测的理由。

## 后续新增 V3 的方式

1. 将共享当前版本提升为 3，更新当前配置类型、校验器和客户端。
2. 在迁移注册表加入 2 → 3 的纯转换，保留原有 1 → 2。历史步骤的输出版本必须固定，不得改成“当前版本”。
3. 在需要时为历史输入保留 Loader schema 字段，不能让宿主在迁移前丢弃/拒绝这些字段。
4. 添加 V2 → V3、V1 → V3、无版本历史 V2 → V3、幂等、输入不变、失败保留和 CAS 并发测试。
5. 若需要新的外部副作用，显式设计执行顺序和可重试性，不把 I/O 放进纯迁移函数。

当前只存在真实的 1 → 2 步骤，不为演示制造无业务意义的 V3。
